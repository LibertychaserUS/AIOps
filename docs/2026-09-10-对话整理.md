# AI CI — 对话整理（2026-09-10）

从一次对齐对话压成可执行约束。不是会议纪要，也不是实现说明。  
仓：`LibertychaserUS/AIOps`（private）。产品仓 GitHub **Verify 不改**。本仓监考（Proctor）不在这里打开。

---

## 1. 要做什么

现有 CI 已经走 GitHub Actions。新系统补两件事：

1. **自动构建测试集**  
   输入：PRD / Figma / user case。  
   输出：集成测试 / 单元测试等**用例**（先给人看，不是直接当门禁红灯）。

2. **自动测试**  
   代码 push 到**可配置**的分支（如 `main`、`test`、`hotfix`）时，跑该分支该跑的集。  
   集的种类：功能集（这次修/新增的）、回归；生产以后才有并发等。  
   我们是 AI Agent 系统：既测产品功能，也测 agent。

只做 **CI**，不做 CD。

## 2. 对话里已经拍板的约束

| 拍板 | 原文意思 |
|---|---|
| 不改现有 GitHub CI | Verify（Typecheck → Lint → Build and test）继续管构建门。 |
| 重点不是「推上去」 | 要真能用起来，能产出。 |
| 人审 AI 用例 | 产品录入需求；AI 出草稿；人看过才能算数。 |
| 失败打回，但不加闲活 | 测试失败挡开发；不要为了流程再造一层开发工作。 |
| 平衡四件事 | 可用性、大家多干的活、token、开发速度。 |
| 支付/登录没做好 | 可以生成并审用例；**不能**把必红测试推进门禁。 |
| 目的 | 不是某个人手写用例，是系统让大家很快产出**好的**用例。 |
| 极简、基本无摩擦 | 理想很大但绕一圈零产出 = 没意义。先做最小、真有收益的一刀。 |
| 工具先借再改 | 参考开源，不必复制；大部分能力 Actions 就能做。 |
| AI 直推 `main` 会踩踏 | 一堆分支也难搞。应有 agent 在云上处理提交，但先不做复杂舰队。 |

多人协作的痛点是：**产品 + 多人开发的信息对不齐**。CodeRabbit / GitLens 能盖住一部分；它们不做的是「需求 → 可审用例」和「push 只跑已批准、已解禁的集」。

## 3. 角色（先认，不先做后台）

- **产品经理**：有地方录入需求（第一刀可以是 git 里一个 inbox 文件，不必先做 Web 工作台）。
- **测试**：目前是虚拟角色；人审 AI 草稿就够。
- **开发**：被测试结果管理；红了修自己的 diff，不被额外流程拖住。

测试用例可以在开发前生成、标 `blocked`；**CI 执行**一定是代码推上去以后。功能没就绪的集不跑、不当红。

## 5. 和已有两套东西的关系

**GitHub Verify（产品仓）**  
已经在跑。本仓不改它、不替代它。

**Proctor（Deepseek3 监考）**  
像半边，不是同一套。它是本机过程账本：七段生命周期、回执、未查、`gate`。监考是程序，**没有理解能力**，**不用模型写账本**。它不从 PRD 生用例，不听 GitHub push，不在云上处理提交。`eval` 测的是 Proctor 自己，不是 Tutor/支付。

本仓复用它的规矩（没证据不过、没审过不跑），不复做一套监考，也不 `attach` 实习工作区。

## 6. 选哪条路

对话问「怎么样做一个好的系统」。三条里选 **A**：

- **A. 薄层叠在 Git 上（采用）**  
  需求进 inbox → AI 出 `draft` → 人审成 `blocked` 或 `armed` → 配置分支 push 只跑 `armed`。token 只在「点生成」时花。push comment 可写「这次碰了谁的包」，减轻踩踏。
- **B. 先做看 main 的云 agent**  
  能防踩踏，但不产出用例。和主目标错位。把「碰了谁的包」并进 A 即可。
- **C. 先做独立 Web 工作台**  
  角色齐全，第一周几乎没测试产出。

不要做成：产品门户 + 虚拟测试角色 + 全套并发/Agent 评测 + 自动改产品代码。

## 7. 第一刀状态机（三种，不许更多）

| 状态 | 含义 | CI |
|---|---|---|
| `draft` | AI 刚写，人没审 | 不跑 |
| `blocked` | 人审过，功能没做好（现在的支付/登录） | 不跑、不当红 |
| `armed` | 人审过，且对应代码声称可测 | 配置分支 push 时跑 |

成功标准：丢一篇已有 PRD 进去，当天有一页人审过的用例；支付/登录是 `blocked`；已落地的（如 My Learning 已合的部分）可以 `armed`；push `main` 不因 `blocked` 变红。

## 9. 同日后续拍板（两棵树 + 只冻契约）

测试体系是一棵树。PRD / 设计 / 功能需求是另一棵树。枝叶形状由接入方文档决定。对上的叶子共用同一个接入方自选的 `function_id`，失败时能指回那片叶子。层次（unit / integration / smoke / k6 / e2e）是同一 id 的面，不是 `E2E-B1` / `UT-007` 第二套编号。

Overlay 是标准件：**冻契约（字段、状态、对齐方式），不冻某产品的编号、PRD 章节树、IEEE 表单名、测试目录。** 人/agent 读接入方文档，编成 `inbox/` + `suites/` 形状即可。`function_id` 只要非空、仓内作为叶子身份唯一、稳定、无空白。不要把 `REQ-n` 或 FR 号段正则写成内核法律。

IEEE：只要识别、层次、双向追溯，不要二十份文档。规格：`docs/test-spec.md`、`docs/agents/overlay-contract.md`、`docs/agents/ieee-test-system.md`。

## 10. 同日后续拍板（Forge 代推必须持有提交密钥）

Overlay 那句「token 只在点生成时花、push 零模型」说的是 **Overlay generate 的模型密钥**，不是 Forge 的 GitHub 凭据。不要混成一把。

开发侧代理提交（`python -m forge submit`，含 `--dry-run`）必须显式持有 **`FORGE_SUBMIT_TOKEN`**（PAT / fine-grained / GitHub App token）。缺或空：退出非 0（fail closed）。不接受本机 `gh auth`、不回落 CI `GITHUB_TOKEN`、也不用 Ops 的 `FORGE_GITHUB_TOKEN` 冒充代推。本地先 `forge check`：check 红不 submit；缺提交密钥也不 submit（两件分开）。Ops merge 是另一套权限。永不打印 token，不写入回执 / PR 正文。不 live-apply Rulesets。
